## 5. PHASE 1 — 공통 엔진의 실제 설계·구현

### 5.1 설계상 시스템 경로

```text
교사 명령(eventId·시각·payload)
  → 명령 형식/권한/중복 ID/revision·writer lease 검사
  → reducer가 다음 게임 상태·순번/이벤트를 계산
  → IndexedDB 단일 readwrite 거래에 상태 + 이벤트 + 체크포인트 기록
  → transaction.oncomplete 확인 이후에만 메모리·교사 화면 성공 반영
  → (추후 구현) 학생 공개 필드만 추린 읽기 전용 동기화
```

**의도:** 원본 이벤트는 감사 대상으로 남기고, 파생 보상/회수 정정은 향후 장부 재계산으로 처리. 현재 PHASE 1에는 '완성된 보상 원장'이 없으므로 설계 의도와 구현 범위를 혼동하면 안 됩니다.

### 5.3 현재 작성한 상태 필드

현재 초기 모델에는 `meta`, `settings`, `world`, `sessions`, `questions`, `attempts`, `teams`, `recovery`, `rewards`, `magic`, `clues`, `eventLog`, `audit`가 있습니다. 다만 **상태 필드가 존재한다고 해당 기능이 작동하는 것은 아닙니다**. 예를 들어 `questions.issuedIds`는 존재하지만 전체 60문항의 균형 출제·복습·오답 회수 알고리즘은 아직 작성되지 않았습니다.

### 5.4 보완한 주요 오류·예방 장치

1. **JSON 복원 원자성**: RUNNING 상태를 먼저 기록하고 두 번째 거래에서 PAUSED로 전환하던 위험을 방지. 복원 일시정지를 만들어 같은 거래에 기록.
2. **eventId 재사용**: 같은 ID/다른 명령·내용은 `EVENT_ID_CONFLICT`로 차단. 진짜 동일 재시도만 중복 처리.
3. **백업 내부 로그 무결성**: ID/순번뿐 아니라 이벤트 유형·시각·내용을 함께 확인해 변조/오류 감지.
4. **시각 역행**: 이전 이벤트보다 빠른 명령 시각은 `CLOCK_BACKWARD` 등으로 차단; 무조건 보정하고 넘어가지 않음.
5. **타이머 끔 상태**: 시간 연장 마법 사용을 차단해 비용만 차감되는 예외 방지.
6. **수업 중 쓰기 소유권**: 오랫동안 명령이 없는 같은 창이 자기 lease를 갱신하고, 다른 창이 소유권을 가져가면 이전 창 저장을 거부하도록 보완.
7. **손상 복구**: 유효 체크포인트 자동 덮어쓰기를 피하고 교사 확인 뒤 손상 원본을 `quarantine`으로 격리.
8. **저장 성공 표시**: 단일 거래 완료 전에는 확정 성공으로 보고하지 않는 코드 경로 구성. 브라우저 UI에서 메시지를 실제 표시하는 기능은 미연결.

### 5.5 핵심 상태의 구별

- **화면 상태**와 **문제 시도 상태**와 **차시 상태**는 분리하고 단순 화면 이동으로 판정·보상을 초기화하지 않음.
- 시도 타이머 단계: `PREPARED → RUNNING ↔ PAUSED → EXPIRED_AWAITING_TEACHER / RESOLVED`.
- 타이머 옵션: 끔/45/60/90/120초; 기본 60초. 만료가 자동 오답을 뜻하지 않음.
- 복원 후에는 교사가 재개하기 전 자동 RUNNING으로 돌아가지 않음.
- 학생 공개 데이터는 화이트리스트 방식이지만, **물리적 화면 복제 중 정답을 숨기는 보안은 보장하지 않음**. 교사 PIN·5분 잠금 또한 아직 구현 완료 아님.

### 6.1 실제 Node 검사

- **환경:** Linux 환경의 Node.js `v22.16.0`.
- **실행 명령:** 신규 모듈/원본 자료를 포함한 로컬 검증 작업 공간에서 `npm test`; 핵심 JS에 `npm run check:syntax`.

- **구성:** PHASE 0 원본 정적검사 6건 + PHASE 1 reducer·세션·모의 IndexedDB 회귀검사 47건.

- **결론:** Node 단위검사는 현재 구현 모듈의 기본적 일관성을 보여주지만 실제 Chrome·Edge·Windows 사용자 환경, 장기간 지속 저장의 안전성까지 증명하지 않습니다.

## 9. PHASE 1 종료를 위한 실제 진행 순서

### 9.1 가장 가까운 작업 — 저장 실증 확보

1. **브라우저 실험 환경 확정:** `file://`/HTTP 접근이 허용되는 Windows Chrome·Edge에서 실험. 먼저 독립 테스트 HTML로 IndexedDB 기본/거래 abort/지속 보관/다중 창 지원 여부를 확인.
2. **진짜 엔진 저장 검증:** 정식 신규 엔진으로 슬롯 I/II/III, revision/이벤트/2세대 체크포인트를 쓰고 페이지 새로고침·완전 종료·복원·중복 창 경합을 시험.
3. **오류 주입/복원:** QuotaExceeded/권한 거부/abort, 손상 로그, JSON 불일치, 타이머 실행 중 강제 종료를 실제 브라우저에서 재현. 실패 때 성공 표시가 없는지 UI와 함께 재검증.
4. **타이머 경계 실측:** 정확히 1초 전후의 이벤트, 일시정지·재개·시간의 모래 20초/4별빛, 복원 시 자동 재개 금지, PC 시간 변경과 장시간 수업 경과를 검사.
5. **결과 기록 및 재검증:** B01~B09의 스크린샷·로그·SHA를 남기고 실패 수정 후 처음부터 회귀 실행. 최소 V09/V11/V12 실증이 통과해야 PHASE 1 완료 후보.

### 9.2 그 이후 — 실제 1지역 완주로 이어가기

- 원본 60문항의 **객관·O/X·연결·순서·분류·단답·교사판정**을 원형 그대로 렌더링하고 교사 판정 흐름 검증.
- 미출제 우선/60소진 복습/미회수 전용 분리·유형/난도 균형·중복 별빛 지급 0 구현.
- 모둠 순환/가로채기 최대1/원모둠 오답 회수 우선·회수 책임 이력 보존.
- 최초 정답/회수 별빛+1, 최초 지역 완료 열쇠+1/별빛0, 다섯 마법 비용·해금 제약 구현.
- 정답 정정 → 파생 보상·가로채기·회수·통계 재계산 → 부족 별빛 정산/사용 차단 구현.
- **한 지역의 준비→문제→판정→회수→결과→중단→복원** 실제 완주 로그를 확보. 이 결과가 PHASE 2 종료 후보.

### 9.3 단계별 승인 게이트 재강조

- **PHASE 1**: V09·V11·V12 실증 없이 저장 엔진 완료 선언 금지.
- **PHASE 2**: V02·V03·V06~V08 및 1지역 V21 부분 완주 없으면 게임 가능 선언 금지.
- **PHASE 3**: 신규 픽셀 PNG 실물·전체 바이트 SHA·GitHub 표시·브라우저 표시·개별 사용자 승인 없이 그래픽 완료 금지.
- **PHASE 4~5**: V01~V21 실측 PASS 없이 전체 게임 완성/최종 운영 승인 금지.
- **PHASE 6**: **사용자 최종 승인 후에만** PR 병합→Railway SUCCESS→실제 운영 URL·저장·접속 검증. 이 각각을 별도 결과로 남김.
